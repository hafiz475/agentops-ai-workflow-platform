2. Why this design was chosen

  • One VM: Railway's free-plan resource limit could not host the API, AI service, PostgreSQL, and Redis together. One Azure VM could run all five containers and use the available Azure credit.
  • Docker Compose: the repository already defined all services, health checks, dependency order, volumes, and internal DNS names.
  • Standard B2ls v2: the originally preferred B2s SKU was unavailable for this subscription in Central India. B2ls v2 was deployable and provided the required 2 vCPUs and 4 GiB RAM.
  • Standard SSD: enough for a Milestone 0 demo while keeping storage cost lower than Premium SSD.
  • Ports 3000 and 3001 only: users need the frontend and API. PostgreSQL, Redis, and the Python service do not need direct internet access.
  • SSH restricted to one IP: prevents the whole internet from attempting SSH login.
  • Systemd: makes the Compose stack return automatically after a VM restart.

5. Cloud-init and Linux deployment

The VM bootstrap installed Git, Docker Engine, and Docker Compose v2; cloned the main branch; created a protected .env with a generated PostgreSQL password; built the containers; and started the stack.

Secret handling: the real generated PostgreSQL password is stored only on the VM and is omitted here. The following is the sanitized, reproducible form of the deployment procedure. 
#!/usr/bin/env bash
set -euo pipefail

apt-get update
apt-get install -y ca-certificates curl git openssl
curl -fsSL https://get.docker.com | sh
usermod -aG docker azureuser

git clone --branch main \
  https://github.com/hafiz475/agentops-ai-workflow-platform.git \
  /opt/agentops-ai-workflow-platform
cd /opt/agentops-ai-workflow-platform

POSTGRES_PASSWORD="$(openssl rand -hex 24)"
install -m 600 /dev/null .env
printf 'POSTGRES_USER=agentops\nPOSTGRES_DB=agentops\nPOSTGRES_PASSWORD=%s\n' \
  "$POSTGRES_PASSWORD" > .env

docker compose up -d --build
docker compose ps

The equivalent custom-data field begins with #cloud-config and invokes these commands under runcmd. Azure processed the custom data with cloud-init during first boot.

Ways to run Linux commands later

Azure portal: VM → Operations → Run command → RunShellScript. This was used to inspect and repair the deployment without opening an unrestricted SSH rule.

SSH from the allowed IP:

ssh -i .\agentops-demo-key.pem azureuser@4.247.145.108

If the home/public IP changes, update the SSH NSG source to the new exact /32 address before attempting SSH. Never change it to Any or 0.0.0.0/0.

6. Automatic startup with systemd

A service unit was created at /etc/systemd/system/agentops-compose.service:

[Unit]
Description=AgentOps Studio Docker Compose
Requires=docker.service
After=docker.service network-online.target

[Service]
Type=oneshot
RemainAfterExit=yes
WorkingDirectory=/opt/agentops-ai-workflow-platform
ExecStart=/usr/bin/docker compose up -d
ExecStop=/usr/bin/docker compose stop
TimeoutStartSec=0

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable agentops-compose.service
sudo systemctl start agentops-compose.service
sudo systemctl status agentops-compose.service --no-pager

Why: Docker restarts with the VM, and systemd reliably recreates/starts the Compose application in dependency order.

7. API health-check failure and permanent fix

Observed symptoms

  • PostgreSQL, Redis, and the AI service were healthy.
  • The API answered successfully from the VM, but Docker marked it unhealthy.
  • The web container did not start because it depends on a healthy API.
  • The systemd unit failed because docker compose up -d reported that dependency failure.

Diagnosis commands

cd /opt/agentops-ai-workflow-platform
sudo docker compose ps
sudo docker compose logs --tail=100 api
sudo docker compose exec api wget -qO- http://localhost:3001/ready
sudo docker compose exec api wget -qO- http://127.0.0.1:3001/ready
sudo journalctl -u agentops-compose.service -n 100 --no-pager

localhost resolved to IPv6 inside the API container while Fastify was reachable over IPv4. Therefore the readiness request worked at 127.0.0.1 but failed at localhost.

Permanent repository fix

The API health check in docker-compose.yml was changed from:

http://localhost:3001/ready

to:

http://127.0.0.1:3001/ready

The change was committed and pushed to GitHub:

15f1212 fix: use IPv4 for API container healthcheck

Update the VM

cd /opt/agentops-ai-workflow-platform
sudo git pull --ff-only origin main
sudo docker compose up -d --build
sudo systemctl daemon-reload
sudo systemctl restart agentops-compose.service
sudo docker compose ps

The VM fast-forwarded from ffbeac5 to 15f1212. The temporary override used during diagnosis was removed, leaving the native Compose file as the source of truth.

11.1 Why OIDC was used instead of a self-hosted runner

The repository is public. A self-hosted runner attached to a public repository increases the risk that untrusted workflow code reaches the VM. The final design uses a GitHub-hosted runner plus Azure OpenID Connect. It stores no Azure client secret and no SSH private key in GitHub.

11.2 Azure identity created in Cloud Shell

Cloud Shell was first registered under Subscription → Resource providers → Microsoft.CloudShell. An app registration and service principal were then created for github-agentops-deploy. 

az ad app list \
  --display-name "github-agentops-deploy" \
  --query '[0].{clientId:appId,objectId:id}' \
  --output json

az ad sp list \
  --filter "appId eq '<AZURE_CLIENT_ID>'" \
  --query '[0].{servicePrincipalId:id,clientId:appId}' \
  --output json

The federated credential was created with the issuer https://token.actions.githubusercontent.com, audience api://AzureADTokenExchange, and the exact subject printed by the GitHub Actions login log: 

az ad app federated-credential create \
  --id "<APPLICATION_OBJECT_ID>" \
  --parameters '{
    "name": "github-agentops-azure-production",
    "issuer": "https://token.actions.githubusercontent.com",
    "subject": "repo:hafiz475@87468194/agentops-ai-workflow-platform@1447357531:environment:azure-production",
    "audiences": ["api://AzureADTokenExchange"]
  }'
Important distinction: GitHub’s AZURE_CLIENT_ID must contain the application/client ID, not the application object ID or service-principal object ID. Registration tokens and private keys must never be copied into this guide.

11.3 Least-privilege Azure role

The service principal received Virtual Machine Contributor only on vm-agentops-demo, not on the subscription or entire resource group. 

VM_ID="$(az vm show --resource-group rg-agentops-demo \
  --name vm-agentops-demo --query id -o tsv)"

az role assignment create \
  --assignee-object-id "<SERVICE_PRINCIPAL_OBJECT_ID>" \
  --assignee-principal-type ServicePrincipal \
  --role "Virtual Machine Contributor" \
  --scope "$VM_ID"

11.5 Workflow behavior

The workflow is stored at .github/workflows/deploy-azure.yml. It uses id-token: write, runs on GitHub-hosted Ubuntu, logs in with azure/login@v2, and invokes Azure CLI Run Command against the VM. 

on:
  workflow_run:
    workflows: [CI]
    types: [completed]
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  id-token: write

jobs:
  deploy:
    if: vars.AZURE_VM_DEPLOY_ENABLED == 'true' &&
        (github.event_name == 'workflow_dispatch' ||
         github.event.workflow_run.conclusion == 'success')
    runs-on: ubuntu-latest
    environment: azure-production

11.6 Safe deployment script on the VM

scripts/deploy-azure-vm.sh rejects an invalid SHA, refuses a dirty production checkout, verifies the SHA belongs to origin/main, fast-forwards to that exact tested commit, rebuilds Compose, starts services, and waits for both endpoints: 

http://127.0.0.1:3001/ready
http://127.0.0.1:3000/

If verification fails, it prints container status and recent API/web logs and exits non-zero, making the GitHub deployment red.

11.7 Failure encountered and exact fix

The first OIDC login failed with AADSTS700016. Two values were corrected:

  1. The GitHub secret was updated to the true application/client ID.
  2. The federated subject was replaced with the exact subject claim shown in the failed GitHub login log, including GitHub’s repository owner and repository numeric identifiers.

After these corrections, the manual deployment passed. A later push passed CI and automatically triggered the Azure deployment, proving the complete chain.

11.8 How to operate the pipeline

  • Normal use: push or merge to main; no manual Azure action is needed.
  • Manual retry: Actions → Deploy Azure VM → Run workflow.
  • Emergency pause: set AZURE_VM_DEPLOY_ENABLED to false.
  • Verify: confirm both CI and Deploy Azure VM are green, then open the frontend, /health, and /ready.

13. Security, limitations, and final checklist

Security controls in place

  • SSH key authentication; no password login.
  • SSH restricted to 115.97.8.157/32 at deployment time.
  • Only ports 3000 and 3001 are publicly allowed for the app.
  • Database, Redis, and AI execution ports are not allowed by the Azure NSG.
  • PostgreSQL password generated on the VM and protected with file mode 600.
  • Trusted Launch, Secure Boot, and vTPM enabled.
  • OS disk, NIC, and public IP configured for cleanup with VM deletion.

Current limitations

  • The site uses raw HTTP and a public IP; HTTPS and a domain are not configured.
  • Milestone 0 has no application authentication or authorization.
  • The frontend is a dashboard shell; workflow execution/model invocation belongs to later milestones.
  • One VM is a single point of failure and is intended for a demo, not a highly available production deployment.
  • PostgreSQL and Redis data reside in Docker volumes on the VM's OS disk; no independent backup was configured.
  • The Azure promotional credit expires; the budget only alerts.
